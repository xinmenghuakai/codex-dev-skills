# Go 测试

## 圈定范围

- 参数是文件、函数或目录时只覆盖指定范围。
- 无参数时综合 plan、未提交/已暂存改动和目标分支 merge-base diff；不要默认使用 `HEAD~1`。
- 读取适用的 `AGENTS.md`、目标代码、同包 `*_test.go`、`go.mod`、测试配置和已有 mock。
- 运行前按 `AGENTS.md` 审查测试收集范围、真实配置、数据库和外部副作用；无法确认安全时停止。
- 如果当前任务只是 Review 且未授权修复、补测或运行测试，只静态检查已有测试，不进入本技能的写入和执行步骤。

## 选择测试方式

- 纯函数或 helper：直接单测，适合时使用表驱动。
- Service：复用已有依赖注入或替身；不得为了测试新增生产接口层或依赖。
- DAO/GORM：复用查询构造 helper、既有 mock 或安全测试库；无法隔离时报告需要集成验证。
- Handler：已有入口测试模式时使用 `httptest` 并保留真实鉴权/中间件边界。

测试与源文件同包、同目录并遵循现有命名。用最少用例覆盖本次业务规则中的正常路径、边界/零值、依赖失败、部分失败、幂等/重复调用、兼容分支和回归场景。断言外部可观察结果，不绑定无关实现细节；不写无有效断言的覆盖率用例。

## 执行

1. 完成上述收集范围、配置和副作用审查并确认安全后，先精确运行目标：`go test -run '<TestName>' ./path/to/package`。
2. 只有副作用审查确认安全时，才扩大到相关包测试、覆盖率或仓库规定命令。
3. 真正仅编译时，对单包使用 `go test -vet=off -c -o <task_tmp_root>/scratch/<package>.test <package>`；`go test -run '^$'` 仍会执行测试二进制及其 `init()`/`TestMain`，必须经过副作用审查，也不得描述成测试通过。
4. 遵循仓库对工作目录、缓存和环境变量的约定；环境问题与代码失败分开报告。
5. 只有用户要求修复生产代码，或 `feature-delivery` 已授权返回实现阶段时，才修改业务实现。

## 输出

列出测试文件、用例对应的业务风险、实际命令与结果，以及未覆盖项、环境阻塞和所需集成验证。严格区分定向测试通过、仅编译通过、未运行和失败。
