# 代码审查

只报告有证据、可触发且值得作者处理的问题；风格偏好和无证据的“可以更优”不算 finding。

## 调用边界

直接调用 `$review` 时使用当前会话能力并明确 `direct_review=true`，不为普通审查强制切换模型。feature-delivery 仅在 `whole|modular` 的正式 Review 中按风险选择 Reviewer；provenance 用于证明实现来源，不用于把普通风险升级到更高模型。产品速度模式由 Codex 自身管理。

## 范围与台账

1. 读取适用的 `AGENTS.md` 和用户指定范围；需求验收以用户原始要求、后续明确纠正及已确认的范围调整为准，先核对 plan/内联契约/任务包是否完整承接。用户说整个文件/模块/后台时覆盖完整相关表面，不缩成最新 diff；仅审代码且未提供需求时完成指定范围的代码审查，说明无法证明需求完整验收，不猜造需求或为此增加确认。
2. feature-delivery Review 存在 plan 时复用“计划交付项清单”，与来源章节及当前有效需求交叉核对；清单本身漏项或错误合并也须报告 finding，不能因全部已列 ID 满足就通过，零 diff 项也须核验。没有 plan 时明确 `plan_coverage_required=false`、`plan_manifest=none`。直接 Review 不建立正式交付项台账，但已提供的需求仍须核对覆盖；无需另建文件、表格、报告字段或审批。
3. 未指定代码范围时综合未提交/已暂存改动、plan 和当前分支相对目标分支 merge-base 的完整 diff；目标分支从 plan、upstream 或仓库约定确认。
4. feature-delivery Review 按仓库、模块和实际涉及的入口、Service、数据、任务、前端与测试建立代码台账；直接 Review 记录指定范围及相关调用边界即可。
5. 沿完整调用链还原业务目标、非目标、数据口径与兼容要求；对“全部/统一/不再使用”等要求，核对同职责的未改代码、旧配置读取、默认值和回退，不能只检查新增实现或同名字段。区分本次引入、已有问题和无法确认的风险。feature-delivery Review 中，当前有效计划项无实现或交付证据属于 `missing`，必须报告 finding；原始需求未被清单承接也须独立报告，尚无计划 ID 时按现有协议使用 `plan_item_ids=none`，不伪造 ID 或自行缩小范围。外部责任方尚待交付标记 `external`，不得宣告发布就绪。
6. feature-delivery Review 在所有计划交付项、适用模块和维度关闭前不输出最终结论；直接 Review 以用户指定范围和必要调用边界关闭为准。先说明真实范围和限制。

feature-delivery 任务包明确 `formal_gate_required=false` 时，仍保留完整范围、计划覆盖和按风险规定的遍数，只省略正式 Gate 文件和输出协议；不套用 direct_review 对计划覆盖的豁免。

### 直接 Review 轻量路径

用户直接要求 Review，且没有 feature-delivery 正式 Gate 任务包时，固定 `direct_review=true`、`plan_coverage_required=false`、`plan_manifest=none`。它可以审查指定文件、非 Git 目录或当前仓库 diff；按实际风险和证据决定检查深度，输出 findings、验证结果与限制，但不要求 snapshot、provenance、外部 no-plan contract、release binding、Review Gate 或机器 report，也不得声称 `release_ready=true`。若用户随后要求发布，先按 feature-delivery 的双向复用规则核对独立性、完整范围、风险维度、验证和当前目标；成立时沿用结论及材料，不为正式发布或高风险测试发布自动补造 Gate。缺失覆盖先补审，仅分流仍要求 `formal_gate_required=true` 时补齐冻结证据和当前报告；direct Review 的名称或一句通过本身不能证明复用成立，也不能充当 Gate。

feature-delivery Review 的计划交付项状态只能是 `satisfied`、清单预先允许的 `not_applicable`、`missing`、`blocked` 或 `external`；存在关联 finding 或验证/依赖阻塞时必须标记 `blocked`，只有当前无已知问题才能标记 `satisfied`。Reviewer 不得自行新增 `not_applicable`；“没有改动”“不在当前仓库”或“由客户端处理”只能形成 `missing/external`，不能作为排除依据。

## 风险与检查遍数

风险由真实状态、失败语义和影响范围决定，不能只按“异步”“消息”或“乱序”等关键词升级。支付、退款、权益、订单归因、表结构/历史回填、跨仓公共契约、生产数据写入、权限或安全边界属于高风险；并发、事务、幂等、状态机和异步链路仅在涉及持久状态竞争、队列/回调、重试补偿、跨实例一致性、重复或丢失会造成不可接受副作用时属于高风险。满足下述全部小修复条件的为 `small`，其余默认为普通风险。

只修复外部服务排序元数据时，若前四项结构和业务条件同时满足，应使用 `normal/2`，不得仅因“消息乱序”升级为 `high/5`；第五项是该风险级别下的验证要求：

1. 调用链在单个请求或 goroutine 内同步串行，不包含队列、回调、调度、重试或跨实例共享状态。
2. 不修改数据库、缓存、业务状态机、资金权益、权限、安全、HTTP/客户端业务契约或不可逆副作用。
3. 外部服务有明确排序字段或协议，本次只补充该元数据，不重新定义业务顺序或失败语义。
4. 旧调用保持兼容，部分失败、超时和后续继续/停止策略没有变化。
5. 安全的定向测试应覆盖请求体、顺序边界、零值/溢出及适用的部分失败。

这类改动仍涉及外部消息语义，不进入 `small/1`。前四项任一结构或业务条件不满足，或排序错误会造成持久状态错乱、重复扣费、权益损失、消息丢失后不可恢复，再升级为 `high/5`；仅第五项测试证据不足时保持 `normal/2`，形成 finding 或 `dynamic_validation=limited/blocked`，不得用提高审查遍数替代缺失验证。

### 小修复快速路径：一遍

只有主 Agent 提供可复核证据且同时满足以下条件，才可把风险定为 `small`：

1. 单仓库，目标分支 merge-base 到当前工作区的完整发布 diff 只包含本次修复，最多 3 个文件且新增/删除合计不超过 80 行；不能把未审查的同分支改动排除在外。
2. 行为目标单一、根因明确，并有覆盖目标分支的定向测试、构建或等价验证证据。
3. 不新增或修改路由、请求响应、错误码、公共类型、配置、依赖、数据库查询/写入、SQL、migration、缓存键、消息/任务、外部调用或跨仓契约。
4. 不涉及资金、权益、订单归因、权限、鉴权、安全、生产数据、事务、并发、幂等、状态机、异步时序、兼容迁移或无法撤回的副作用。
5. 初审没有未关闭的既有 finding；复审只允许核验本轮 `small` Review 产生且修复未扩面的 finding。影响范围必须能限定为改动符号及其直接调用方/被调用方；任一条件缺证据或 Reviewer 发现影响面更大，立即升级为 `normal` 或 `high`。

小修复只执行 `targeted_fix`：检查完整发布 diff、改动符号的直接调用边界、原问题触发条件、回归风险和定向验证。允许用任务包内联的修复契约代替整份 plan 台账，固定 `plan_coverage_required=false`、`plan_manifest=none`；不得因此忽略发布 diff 中的任何文件。文案、注释或日志文本只有在不影响解析、协议、监控告警和业务分支时才可走此路径。

以下固定 pass ID 和遍次只用于 feature-delivery Review。直接 Review 记录范围和主要风险，沿相关调用链检查到足以支持结论；发现更大影响面时扩展检查，不为满足遍数重复审读。正式流程的 baseline、scope 和输出协议见下述引用文件。

### 普通风险：两遍

1. **完整检查遍**：覆盖意图与契约、状态与失败、数据与集成、SQL/migration、性能和测试反证。
2. **零基础复核遍**：暂时忽略已有 finding，从完整代码和 diff 独立寻找不同类型反例，再去重合并。

### 高风险：五遍

1. **意图与契约**：业务目标、鉴权、请求响应、数据口径、兼容、非目标和跨仓入口。
2. **状态与失败**：状态机、事务、幂等、并发交错、重复/乱序、重试、部分成功和补偿。
3. **数据与集成**：读写范围、逻辑删除、时间/时区、空值、历史数据、外部依赖和前后端业务码；migration 分别检查新库、旧库、部分升级和重复执行。
4. **测试反证**：从风险反推缺失用例，确认断言真实经过目标分支，并区分未运行、仅编译、阻塞和通过。
5. **零基础复核**：忽略前四遍 finding，再做一次完整反例检查并去重。

所有遍次完成后一次性汇总，不得发现首批问题就停止。涉及 GORM、SQL、索引或 migration 时，在用户可见结论前完成 `sql-check` 并合并结果。

固定 pass ID：

- 小修复：`targeted_fix`
- 普通风险：`full_surface,clean_room`
- 高风险：`intent_contract,state_failure,data_integration,test_counterexample,clean_room`

## 核心维度

- 数据：过滤、关联、重复、聚合、时间、空值、默认值、状态、逻辑删除和历史兼容。
- 契约：鉴权、校验、必填/类型/枚举、错误码、客户端与前端兼容。
- 并发与稳定性：事务、锁、goroutine、幂等、重试、超时、资源释放、错误与日志。
- 安全与性能：越权、注入、敏感信息、开放任务、N+1、无界查询和热点竞争；性能结论需要证据。
- 测试与注释：关键分支是否真实验证，业务关键处是否满足 `AGENTS.md` 的注释规则。

## 审查事实复用

首轮审查就记录可复核基线：实际 Reviewer、仓库与目标 ref/SHA、merge-base、候选 commit/tree、完整审查范围、需求口径、已完成维度、findings 和验证依据。未提交内容保留对应 diff/文件摘要及未跟踪文件；验证注明输入、命令和环境。记录放在现有回传或证据位置，普通审查不为此创建正式 Gate 文件。

已审代码换目标发布时，先由主 Agent 按 [双向复用与发布检查](../feature-delivery/references/review-and-release.md#双向复用与发布检查) 核验；条件满足不重启 Reviewer。需要补审或复审时由一个独立 Reviewer 汇总结论；单一审查来源优先交回原 Reviewer，多来源合版不要求逐个重启原 Reviewer。由当前 Reviewer 比对首轮基线与当前完整目标 diff、相关调用链、配置/依赖、契约和验证输入；不能仅凭分支名、文件名或“已经审过”判断相同。没有可核对基线、首轮覆盖不足或 Reviewer 无法验证继承结论时，补齐缺失维度；无法界定影响面时重新完整审查。

复用同样适用于跨窗口/跨会话：读取各来源的实际审查结果、代码基线和验证依据，映射到当前完整发布范围；来源和覆盖能核验的未变部分按下述风险规则继承，补查未审范围、变化及合并后的交互。只给出“审过/通过”的摘要不足以复用。证据缺失时先补查缺失部分，不能仅因来自另一窗口重做已证实有效的检查；重要语义冲突或影响无法界定时仍完整复审。

- **内容与语义未变**：复用已完成的分析与有效测试，只核对最终范围、目标分支独有提交、合并结果及适用构建产物。此前未覆盖的目标集成仍须检查。
- **普通风险且变化有明确边界**：核验旧 finding 的修复、变化及受影响调用方/被调用方，并针对最终集成补做反例检查；其余已证明未变的表面复用。最终 `full_surface,clean_room` 覆盖全部当前范围，不要求把未变化代码再次逐行审读。
- **高风险内容发生变化、契约/权限/数据写入/持久并发等关键语义变化、重要合并冲突、风险升级，或影响面无法界定**：按当前完整范围重做规定的 2/5 遍。高风险未变代码及其相关契约、调用链、运行语义均有证据时可复用五遍事实；仅目标分支、合并 SHA 或符合既有规则的环境构建变化不自动使业务审查失效，不得把高风险语义修复当成普通增量。

未关闭 finding 继续阻塞发布；复用结论必须列明原基线、已核对未变范围、本轮实际检查和验证限制。`completed_passes` 表示继承证据加本轮核验已覆盖最终全部规定维度，不能伪称重新执行了整轮审查；直接 Review 没有覆盖相应维度时不得自动补齐 pass ID。

test/master 双向发布复用原始审查及验证材料，按上述分流只补目标检查记录，不生成新 report、provenance、快照或 binding。确需新的正式 Gate 时仍绑定当前候选，实际 Reviewer 出具对应报告；主 Agent 不得修改旧 scope/指纹或声称旧 binding 已覆盖新目标。只补充验证记录、接口说明或构建清单时，核验新增材料及其影响，代码未变不重做代码检查；新材料揭示问题时按实际风险处理。

## 复审与完成门槛

修复后先验证旧 finding 和必要回归测试。feature-delivery 的 `small` 仍按完整短 diff、旧 finding 和直接调用边界检查，资格失效时升级；`normal/high` 按上节比对完整台账，决定复用或完整复审。`direct_review` 同样核对指定范围及受影响调用边界，非 Git 范围不得伪造 merge-base。

首次审查的 finding 来源统一标记为 `initial`。复审时标记为 `baseline`（修复前已存在但此前漏报）、`fix_introduced`（本轮修复引入）、`newly_exposed`（修复后才可触发）或 `unknown`；来源不确定时不得把问题归因给修复。

收尾须同时核对“实现是否正确”和“当前有效需求是否完整实现”，并检查验证是否能反证被禁止的旧行为仍然存在；缺少必要验证时报告缺口，不能以编译或已有测试通过代替验收。只有改动文件、受影响调用链、plan 仓库和所有适用维度均有证据、验证或明确阻塞，适用的 `sql-check` 已合并，且没有因发现问题而跳过剩余范围时，才可结束。`dynamic_validation=completed` 表示本次 scope 内所有必要、已授权且可安全执行的动态验证已完成；明确排除的真实外部服务端到端、发布后人工验收或与本次发布无关的本地生成工具，可列为非阻塞限制，但不能因此降为 `limited`。只有 scope 内必要验证尚未执行或证据不足时才使用 `limited/blocked`；动态验证受阻时只能给受限静态结论，不能无条件写“审查通过”。

## 输出与正式流程

直接 Review 按 P0-P3 严重性输出有证据的 findings：文件行号、触发条件、影响、问题来源和最小修复方向；另列实际覆盖范围、验证结果和限制。没有问题时明确未发现需要报告的问题，不把未运行的验证描述成通过。

只有接到 `feature-delivery` 且 `formal_gate_required=true` 的正式 Review 任务包时，才必须在开始审查前读取 [正式 Review Gate 协议](references/formal-gate.md)，执行其中的冻结证据、作用域提升、报告格式和发布绑定要求。直接 Review 不读取该协议，也不生成 Gate 或发布就绪结论。
