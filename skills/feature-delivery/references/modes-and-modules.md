# 交付模式与分模块验收

仅在主 Agent 已判定 `delivery_mode=modular`，或需要复核 targeted/simple/whole/modular 边界时读取本文件。

本文所有“必须委派 Planner/Architect 回写 plan”的要求均受 SKILL.md“轻量方案维护”例外约束：已有事实和已确认口径可由主 Agent 直接回写；新增高风险取舍仍按原路由。此例外不降低业务实现、验收、来源记录或发布门禁。

## 模式边界

- `targeted_fix`：单仓、单个已有读接口或内部读逻辑，method/path、鉴权/中间件、请求/响应字段形状和错误码不变，只调整筛选、排序、分页、结果覆盖范围或既有数值参数范围。业务实现最多 3 文件/80 行，且不涉及配置、数据、缓存、消息、任务、外部调用、权限、事务并发幂等、异步、兼容迁移、跨仓或不可逆副作用。固定 `execution_lane=single`；当前主 Agent 完成最小实现、定向验证和短 diff 核对，不进入正式 Review Gate。完整细则见 [轻量行为修复](targeted-fix.md)。
- `simple_fix`：单仓、单一根因、可在当前回合完整核对的短 diff；业务实现最多 3 个文件且增删不超过 80 行，测试文件和同一既有非敏感配置项在多个环境文件中的机械同步不计入业务实现上限。允许在现有调用方式不变时调整已有模型名、超时、批量大小等运行参数；不得新增密钥、地址、依赖、协议字段、重试/并发策略，或改变数据、权限、资金、异步和不可逆副作用。固定 `execution_lane=single`。当前主 Agent 使用当前会话模型完成实现、必要补测、一次安全定向验证，并核对完整短 diff、直接调用边界和验证结果；不固定派发 Implementer、Verifier 或 Reviewer，不启动正式 Review Gate。
- `whole`：单一完整业务链路，虽跨多个代码层但需要共享上下文、连续语义判断或公共文件修改。固定 `execution_lane=single`，一个执行者覆盖完整授权范围；按主文件“验证执行方式”，普通 L2 的现有模式补测、安全定向验证及构建由原执行者连续完成，包含契约不变的普通前后端两仓；独立环境或明确并行收益时交 Verifier，复杂测试设计和不明确失败交 Test Specialist。无法安全执行时报告阻塞。复用有效验证证据后仍执行与风险匹配的独立 `normal/high` Review。
- `modular`：多个可独立描述与验收的业务模块、需要独立验收的跨仓库/多客户端，或需要缩小单次风险面的高风险链路。必须先有已确认 plan、原子计划交付项清单、依赖图和公共改动归属；只有此模式可选择 `execution_lane=serial|parallel`。

整体实现是默认模式。不能因为技术方案按模块写、存在多个文件或多个计划项，就自动使用分模块实现。证据不足时只能从 `targeted_fix -> simple_fix -> whole -> modular` 升级，不得为节省 Token 降级风险。

## 串行与并行

1. `execution_lane=serial` 和 `execution_lane=parallel` 只允许 `delivery_mode=modular`；收到 `targeted_fix|simple_fix|whole` 加这两个 lane 的任务包必须拒绝，不得把“多个文件/测试步骤”解释为模块化。
2. 在 modular 中，依赖未就绪、会修改同一文件/生成物/公共模型、共享数据库，或接口契约未冻结时使用 `execution_lane=serial`。
3. 在 modular 中，只有输入输出契约稳定、写入范围互斥、可独立验证且不读取另一并行模块未提交产物时，才使用 `execution_lane=parallel`。默认每波最多 3 个实现 Agent，并受运行时并发槽限制；不得按模块总数直接启动同数量 Agent。
4. 并行任务包必须声明 `wave_id`、唯一 `current_module_id`、`allowed_plan_item_ids`、`dependency_status=ready`、精确 `write_scope` 和 `shared_contract_baseline`。主 Agent 独占 plan 变更决策、公共文件和跨模块契约修改权；仓内 plan 的实际写入只能由定向 Planner/Architect 完成。
5. 每个模块按 [模型分级与 Agent 路由](model-routing.md) 独立记录 `task_difficulty`、`selected_agent`、`selected_model` 和 `selection_evidence`；不得因为总需求复杂，就把十个简单模块全部交给 Astra，也不得因为某个模块简单，就降低共享契约或高风险模块的模型。
6. 共享工作区只在写入范围确认互斥时并行；已有独立 worktree 才能按隔离目录描述，并给出真实绝对路径和同步方式。不得虚构隔离环境或承诺自动合并。
7. 每个模块使用同一模块 ID 和计划项 ID 定向验证。发现契约冲突、越界修改、依赖失效或验证失败时，停止当前波次的新派发，由主 Agent 收敛公共问题；代码、测试、配置、依赖和验证命令未变化时复用已有有效证据，不重复生成。
8. 并行只缩短墙钟时间，不视为节省 Token。能用 2 个 Agent 完成时不启动 3 个。

## Migration 默认复杂度

- 用户未明确要求时，migration 采用最简单、可重复执行的 SQL，只覆盖当前需求的新增或必要字段调整；不为并发执行、半执行历史、异常旧资源恢复、命名锁、主动失败门禁或自动修复增加控制流。
- migration 由发布流程串行执行。发现旧库异常时报告并人工处理；只有用户明确要求兼容、修复或校验时才增加相应逻辑。

## 模块实现与验收

同批上线按 [同批上线与跨窗口合版](review-and-release.md#同批上线与跨窗口合版) 安排一次最终完整 Review；逐模块保留定向验证和风险核验，已有审查按证据复用。

1. 整个需求继续使用同一份 plan、仓库/分支集合和发布范围；模块化交付不等于拆期。
2. `serial` 模块等待直接前置模块验证通过；`parallel` 模块按波次执行，同一波完成前不启动依赖该波结果的模块。
3. 每模块完成后执行定向测试、编译检查和风险核验，并回传模块覆盖、验证和验收事实；至少覆盖数据口径、失败处理、幂等/并发和已完成模块的契约，涉及 SQL/索引/migration 时执行 `sql-check`。Implementer、Tester、Verifier 和 Reviewer 不得直接改 plan。
4. 主 Agent 要回写仓内 plan 时，必须把实际模块回传交给定向的 Planner/Architect 作为“事实性 plan 回写”任务。该 writer 默认在原模块下写“验收记录”，状态为“待验收”，包含完成/未覆盖范围、环境入口、步骤、预期、验证证据、限制、仓库分支、拟提交范围和模块/计划项 ID；只可写已发生的事实，不得借回写改变业务口径或伪造 Commit SHA。该 plan 进入 release diff 时，writer 必须返回一条 `entry_type=scope_contract`；同一 plan 的多阶段记录允许有多条 Planner/Architect contributor 来源条目。未提交时写“待验收通过后生成”。正式 Commit SHA 只在模块回传和最终交付中报告，不得回填到生成该 SHA 的同一个提交中。
5. Codex 自测、Review 和验证不能代替用户验收。用户确认后，主 Agent 再委派 Planner/Architect 将该确认事实写为“验收通过”；不通过时记实际现象并标“待修复”。任何影响业务表现、接口契约或验收步骤的后续改动都必须记录原因，并把验收状态重置为“待验收”；纯文档/机械调整只有 plan 记录依据后才能保留原结论。
6. 已获得逐模块本地提交授权时，人工验收通过、由 Planner/Architect 完成 plan 回写后，先检查全部受影响仓库的变更范围，再按仓库分别创建该模块的正式本地提交。每个提交只含本仓的模块代码/测试；plan 在仓库外时不得复制进代码仓。未授权或验收未通过时不得提交。
7. 必须依赖远程测试环境时，取得用户对延期验收的明确授权后，可记录定向验证及“待验收”并创建待验收提交。全模块汇总后按当前风险审查，已有结果优先按 [双向复用与发布检查](review-and-release.md#双向复用与发布检查) 核验，不能因切换 test/master 自动重审或重建材料。测试发布只允许已授权的 push/test 及独立测试部署，多仓由主 Agent 按仓执行 `git-pr test`；不调用 `release` 或 Release Coordinator。远程验收通过后回写既有 plan 的真实结论，核对 master 完整范围、集成与生产前置项；复用成立则直接沿用审查，否则按当前风险补审或完整复审，并仅在入口要求时生成正式 Gate。测试失败时保留已推送历史，修复、验证并关闭问题后再按同一规则发布；测试授权不自动覆盖 master/tag。
8. 默认复用原 plan 保存验收记录；只有用户明确要求或材料需要跨团队流转/签字/多环境归档时，才生成独立验收文档，且不能替代原 plan 状态。
9. 模块验收不替代最终完整 Review、SQL 审查、端到端验收或发布授权。
10. 全模块完成后，必要且安全的跨模块验证、独立审查或有效复用须覆盖全部最终代码、plan 和验收状态；按入口判定是否需要新的 `final_release` Gate。
11. 用户明确授权无需逐模块停顿时，可记录“待验收”后继续，但不得创建正式模块提交；最终按真实逻辑/仓库边界提交，不承诺“一模块一正式提交”。用户要求一模块一正式提交时，必须逐模块停顿、人工验收后提交，二者不得同时执行。
