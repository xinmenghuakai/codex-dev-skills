# 轻量行为修复

`delivery_mode=targeted_fix` 用于已有能力的窄行为修正，目标是让“改查询方法/排序/分页”不被全量交付仪式放大；它不是放宽高风险改动的捷径。

## 准入条件

以下条件必须同时满足：

1. 只涉及一个仓库和一个已有 HTTP 入口或内部读逻辑；只改变查询筛选、排序、分页、结果覆盖范围，或已有数值参数的有效范围。
2. method/path、鉴权和中间件、请求字段、响应字段形状、状态码/业务错误码保持不变；允许返回的既有列表项增减或顺序改变，但不得新增/删除/改名字段或改变字段类型、空值语义。
3. 业务实现最多改 3 个文件、增删不超过 80 行；测试、针对旧行为的一行 plan 勘误或本地生成物不计入该业务实现上限，但必须逐一读取，且不能夹带无关改动或任何契约变化。
4. 不涉及配置、依赖、model/表结构、DDL/migration、数据写入或回填、缓存、消息/任务、外部调用、资金权益、权限安全、事务/并发/幂等、异步状态、兼容迁移、跨仓或不可逆副作用。
5. 能在直接代码和 Git diff 中确认根因、允许修改范围与安全验证方法；证据不足不猜测，直接升级。

## 最短执行链

先写一段默认不落盘的短范围锁定：目标、保持不变的传输契约、允许调整的行为、禁止项、目标文件/函数、当前业务实现行数，以及定向验证命令和副作用判断。用户明确要求保存短计划时，按 SKILL.md“Plan 与任务包”的短计划规则写入约定位置，不升级模式或触发完整模板与审计。

随后由当前主 Agent 完成最小修改；只运行已审查安全的现有定向测试，或受影响包的编译/构建。必须执行 `git diff --check`，并对完整 diff 做一次短核对：筛选条件、排序规则、分页/上限、零值/边界值、错误回退和无关工作区是否被保留。没有安全测试命令时，如实报告“仅编译/静态核对”，不得虚报测试通过。

此模式不默认创建版本 plan、任务包、provenance、快照、Review Gate、YApi/ApiPost 产物，不派 Implementer、Verifier、Reviewer 或 Test Specialist。已有 plan 仅在明确写错受影响旧行为时改正那一条；不得借此扫描或补齐版本其他模块。

## 接口交付与发布

稳定传输契约下的行为修复不自动调用 `api-handoff`，也不自动同步 YApi、ApiPost 或前端变更表；用户明确要求接口交付或同步时才执行。

用户要求发布到 `test`、`master` 或指定分支时，仍重新确认准确 Git 目标，并按 `git-pr` 的正常流程完成预检、合并、tag（适用时）和远端读回。该模式只跳过 feature-delivery 的正式 Review Gate，不跳过发布授权或 Git 检查。

## 立即升级条件

出现下列任一项即停止轻量流程，重新按更高模式组织：

- 新增/删除路由，或请求/响应字段、鉴权/中间件、错误码、状态码、空值语义改变；
- 新增依赖或修改配置、model、数据库、缓存、消息、任务、外部服务、写数据、权限、并发/幂等或异步状态；
- 业务实现超过 3 个文件或 80 行，或测试/辅助 diff 大到无法在当前回合逐一核对；
- 定向测试需先设计，测试有外部副作用，编译/测试失败，或验证结果无法区分实现与环境问题；
- 实际影响不止一个已有读行为、跨仓，或根因与排序/筛选/分页口径仍不明确。

升级顺序只能是 `targeted_fix -> simple_fix -> whole -> modular`。`targeted_fix/simple_fix` 均不进入正式 Review Gate；Review 中的 `risk_level=small` 和 `pass_ids=targeted_fix` 属于审查协议，不代表本交付模式，也不得据此给简单修复添加正式 Gate。
